§Overview

This is a RAG system — Retrieval-Augmented Generation. Instead of asking Claude a question cold (where it can only answer from what it learned during training, and might invent numbers), you first retrieve the exact transcript passages relevant to the question, hand those to Claude as context, and instruct it to answer only from what's in front of it. That's the mechanism behind the PRD's core requirement: “answer only from retrieved context — no hallucinated figures.”

There are exactly two pipelines, and they only ever meet at one place: the vector store.

  • INGESTION  runs once, offline, whenever a new transcript PDF is added. It reads, chunks, and embeds the transcript, then writes it into the store.
  • QUERY  runs once per user question, live. It embeds the question, searches the store for the closest chunks, and asks Claude to answer using only those.

§Ingestion, step by step runs offline

Triggered by python -m src.ingest. For every PDF under cocnall-scripts/<TICKER>/, this runs once and writes chunks into Chroma. Walking through src/parse.py, src/chunk.py, src/embeddings.py and src/store.py in call order:

1

extract_pages() parse.py

Opens the PDF with pdfplumber and pulls raw text out of every page. At this point it's just a list of strings, one per page — no structure yet, just what the PDF's text layer contains.

2

split_cover_and_body() parse.py

Every transcript PDF here is a SEBI Regulation-30 filing: a cover letter to the stock exchanges, a title page listing management attendees, then the actual dialogue. This function separates the two by scanning each page for markers like "MANAGEMENT:" — pages that have it are metadata pages, everything else is transcript body.

extract_metadata() then regexes the cover text for the quarter (Q\d\s*FY\s*\d{2,4}), the actual call date, and the management roster — so quarter/date come from the document itself, not a guess based on the filename. This mattered in practice: two of the six source PDFs turned out to be byte-identical duplicates filed under different names, and one filename's date didn't match its content at all.

3

clean_body() → parse_speaker_turns() parse.py

clean_body() strips page-number footers, repeated header lines (company name, date) that PDF extraction reinserts on every page. parse_speaker_turns() then walks the cleaned lines looking for the pattern "Name: text" at the start of a line — every time it matches, that's a new turn; everything until the next match is that speaker continuing. Output: a plain list of (speaker, text) pairs, e.g. ("Narendra Mantri", "Our EBITDA margin for the quarter was...").

find_qa_start() then scans those turns for the moderator's hand-off line (phrased inconsistently across quarters — "question-and-answer session" in some, "the first question is from…" in others) to split prepared remarks from Q&A.

4

chunk_turns() chunk.py

This is the retrieval-quality decision. Two different chunking rules, by section:

  • Prepared remarks: one chunk per speaker turn — each is already one person's continuous thought.
  • Q&A: one chunk per exchange, not per turn — the analyst's question and the full management answer (including any back-and-forth) are merged into a single chunk, bounded by the moderator's "next question" transitions. Split a Q&A into separate question-chunk and answer-chunk and you can retrieve the answer without the question that gives it meaning.

A single monologue can run to 2,000+ words with no natural break, which is both bad for retrieval precision (one giant chunk about "the CEO's opening remarks" matches everything and nothing) and can blow past an embedding provider's per-request token limit. So _emit() checks every candidate chunk against a 1,600-character cap and, if it's over, _pack_sentences() greedily re-packs it into multiple sentence-aligned pieces that share the same speaker/quarter/section metadata. Target: roughly 150–400 tokens per chunk — a coherent thought, not a fragment, not a wall of text.

# the shape every chunk ends up in, e.g.:
{
  "chunk_id": "JINDALSAW_Q2FY26_QA003",
  "ticker": "JINDALSAW", "quarter": "Q2FY26", "fiscal_year": "FY26",
  "call_date": "2025-10-23", "speaker": "Bhavik Shah",
  "speaker_role": "Analyst", "section": "Q&A",
  "text": "Bhavik Shah: The next year CAPEX will be...\nVinay Kumar: I think..."
}
5

embed_documents() → upsert_chunks() embeddings.py · store.py

embed_documents() sends chunk text to Voyage in batches of 15 (small on purpose — the free API tier caps at 3 requests/minute and 10K tokens/request; a batch that's too large or too frequent gets rate-limited, so _embed() retries with backoff and ingest.py sleeps between batches). Each chunk of text comes back as a 1024-number vector.

upsert_chunks() writes {id, vector, text, metadata} into the Chroma collection, keyed by the stable chunk_id built in step 4. Re-running ingestion on the same PDF overwrites the same IDs rather than duplicating — that's what makes the whole pipeline safe to re-run.

§Query, step by step runs per question

Triggered every time you hit Enter in the chat UI. All in src/query.py, calling out to embeddings.py and store.py.

1

embed_query() embeddings.py

The question text goes through the same Voyage call as ingestion, just with input_type="query" instead of "document" (Voyage optimizes the vector slightly differently for each, but both land in the same 1024-dimensional space). One question in, one 1024-number vector out.

2

retrieve() → vector_query() query.py · store.py

Chroma compares the question's vector against all stored chunk vectors using cosine similarity — the angle between two vectors, not their distance (see below) — and returns the closest top_k (default 8). If the UI's ticker/quarter filter is set, that becomes a metadata where clause, so the search only ever considers chunks matching e.g. quarter = "Q2FY26" — this is what lets a query be scoped to one company or one quarter without re-searching everything, straight out of PRD 5.3.

store.query() converts Chroma's raw distance into a 0–1 score (1 - distance) attached to each returned chunk, purely for display in the Sources panel.

3

_format_context() + system prompt query.py

The retrieved chunks get formatted into labeled blocks — [Q2FY26 | Narendra Mantri (Management) | Prepared Remarks] followed by the chunk text — and concatenated. This, plus the user's question, becomes the message sent to Claude, paired with a system prompt that does the actual grounding work:

Rules:
- Answer only using the provided excerpts. Never use outside
  knowledge or invent figures.
- Every factual claim must carry an inline citation in the
  form (Quarter, Speaker).
- If the excerpts don't contain the answer, say so plainly
  instead of guessing.

This is the whole anti-hallucination mechanism, in plain sight: not a filter bolted on afterward, just an instruction plus the fact that nothing except the retrieved text is in the prompt for the model to draw on.

4

client.messages.create() query.py · anthropic SDK

The actual call to Claude (claude-sonnet-5). The response comes back as a list of content blocks — the code picks out the text block specifically (next(b for b in resp.content if b.type == "text")) rather than assuming the first block is the answer, since a response can include other block types alongside the text.

5

Back to the UI app.py

answer() returns {"answer": …, "sources": hits} — Streamlit renders the text directly under the chat bubble, and the source chunks (with quarter, speaker, role, section, relevance score) go into the collapsible "Sources" panel underneath. Nothing in the UI is invented at this layer; it's just displaying exactly what steps 1–4 produced.

§Concepts worth knowing cold

The vocabulary that turns "I built a chatbot" into a conversation an interviewer will take seriously.

Embedding

A function that turns text into a fixed-length list of numbers (here, 1024 of them) such that texts with similar meaning end up with similar numbers — not similar spelling. "Debt reduction" and "paying down borrowings" land near each other even though they share almost no words. This is what makes semantic search possible at all: you're searching by meaning, not keyword match.

Cosine similarity

Two vectors, both anchored at the origin, form an angle. Cosine similarity is the cosine of that angle: 1.0 if they point the exact same direction (same meaning), 0 if perpendicular (unrelated), negative if opposite. Crucially it ignores vector length and only cares about direction — which is why it's the standard choice for comparing embeddings, where length is mostly an artifact of text length, not meaning.

Chunking strategy (fixed-window vs. semantic)

The naive RAG approach splits documents every N tokens, regardless of what's mid-sentence. This project instead chunks on structural boundaries — speaker turns, Q&A pairs — because a transcript's real unit of meaning is "what one person said" or "one question and its answer," not "the next 300 tokens." Retrieval is only as good as the chunks it's choosing between; a chunk that starts mid-thought hurts every downstream answer that draws on it.

Metadata filtering

Every chunk carries structured fields (ticker, quarter, speaker role, section) alongside its vector. Chroma's where clause lets a search be vector similarity within a filtered subset — "closest matches, but only from Q2FY26" — rather than re-ranking the whole corpus and hoping the right quarter surfaces near the top. This is what makes the ticker/quarter dropdowns in the UI actually work, and it's the exact mechanism PRD Phase 3 (scaling to a watchlist) depends on.

Grounding / anti-hallucination

Not a separate system — just prompt design plus context control. The model is never given the freedom to answer from its own training knowledge because the instructions explicitly forbid it and the only facts in the prompt are the retrieved excerpts. If retrieval returns nothing relevant, the code short-circuits before ever calling Claude (if not hits: return "No relevant transcript chunks found") rather than letting the model try anyway.

Idempotency

Chunk IDs are deterministic ({ticker}_{quarter}_QA003, etc.), so re-running ingestion on a PDF you've already processed overwrites those IDs in Chroma instead of creating duplicates. This is what makes "just re-run ingestion" a safe answer to "the parser logic changed" — a property you want in any pipeline that might run more than once against the same input, and worth naming explicitly if asked about production-readiness.

§Interview talking points

Framed as things you decided and can defend — not just things that happened.

“I chunked by speaker turn and Q&A pair instead of fixed token windows, because a transcript's natural unit of meaning is a person's full thought, not an arbitrary word count.”
Shows you understand retrieval quality is a chunking problem before it's a model problem.
“I derive quarter and call date from the document's own text, not the filename — I found duplicate and mislabeled source files during ingestion that filename-based logic would have silently gotten wrong.”
A concrete data-quality bug you caught, not a hypothetical.
“Grounding isn't a filter I bolted onto the model's output — the model literally has no other facts available to it than the retrieved chunks, plus an explicit instruction to cite every claim.”
Distinguishes prompt-level grounding from post-hoc fact-checking — a real distinction interviewers probe for.
“Metadata filtering runs inside the same vector search, not as a second pass — so scoping a question to one quarter doesn't mean re-ranking the whole corpus.”
Signals you know retrieval and filtering are one operation, not two.
“Adding a second company is zero code changes — drop PDFs in a new ticker folder and re-run ingestion — because metadata comes from the document, chunk IDs are namespaced by ticker, and the store is schema-less beyond that.”
This is literally PRD Phase 3's exit criteria, and you can point at the code that satisfies it.
